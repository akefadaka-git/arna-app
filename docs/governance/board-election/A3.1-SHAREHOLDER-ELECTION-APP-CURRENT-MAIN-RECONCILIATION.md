## 1. Current-main finding

App main contains Shareholder Workspace and Portal functionality and general Governance body/attendance/people views. It contains **no Board Election-specific route, API adapter, component, Workspace, Portal page, or Admin page**. The existing Governance feature client is for governance bodies, terms, positions, appointments and memberships; it is not an election API client.

The App must not represent PR-only Board Election UI as delivered functionality. Backend API policy and decision state remain authoritative.

## 2. Workspace contract

A3.4 should add a dedicated election feature area and typed API adapter, after A3.2/A3.3 API contracts stabilize. Required surfaces:
- tenant-scoped election list and detail;
- authority evidence and rule-version status;
- committee and candidate workflow where backend endpoints/permissions exist;
- register preparation/reconciliation/freeze status for authorized roles;
- source provenance and explicit stale/unverified/conflicting/blocked exceptions;
- audit references and clear separation of candidate eligibility from voter eligibility.

No frontend-derived eligibility, vote-weight, quorum, tally or certification logic is permitted. Do not display an action unless the API allows it and the applicable legal/operational gate is closed.

## 3. Shareholder Portal contract

Add a read-only “My Board Elections” page only after the API exposes a stable authenticated identity contract. Resolve the current holder/person server-side; never accept shareholder identity from a route parameter or client payload. The page may show authorized notices, election status, proxy/attendance instructions, and certified/published results only where the API explicitly supports those states.

No ballot submission, voting weight, candidate eligibility assertion or “eligible” badge is to be shown while the backend/legal decision is unresolved. No portal-side calculation from current holdings.

## 4. Admin boundary

The Admin Console may show technical health, missing evidence and integration exceptions under explicit technical permissions. Technical administration does not confer authority to verify the statutory register, appoint a corporate committee, approve candidates, freeze the electorate, open ballots, count votes or certify results.

## 6. Acceptance criteria for A3.4

- Workspace routes/navigation require exact least-privilege Governance permissions; backend authorization remains authoritative.
- 401/403/404, cross-tenant, stale-source, unresolved-rule, frozen and exception states render accurately.
- Client-supplied shareholder IDs cannot override authenticated server identity.
- Candidate eligibility and voter eligibility are not conflated.
- No ballot/vote weight/quorum/tally/certification control appears without explicit API state and closed legal/operational gates.
- Portal shows only the authenticated user's permitted data.
- Admin technical privilege cannot bypass corporate approvals.
- Amharic-first/English fallback, keyboard and screen-reader support, responsive behavior and WCAG 2.2 AA tests pass.
- Notification links preserve authorization and do not expose private shareholder data.
